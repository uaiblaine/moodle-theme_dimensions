### 1.2 A queued default move survives the setting being changed back
- File: `classes/local/focusmodefields.php:196` (batch b08), reported as **risk**
- Verdict: **confirmed**, severity after refutation: **risk**
- Evidence: if ($old === (int) $new) { return; } ... \core\task\manager::queue_adhoc_task($task, true); return;  The task's execute() calls set_default((bool) $data['new']) without re-reading the setting.
- Suggestion: Sequence on a site above MATERIALISE_INLINE_LIMIT: an admin turns the setting on (task queued, field still 0), then turns it off before cron. sync_default(false) sees old 0 === new 0 and returns, and cron then moves checkbydefault to 1 against the setting. Fix: have the task compare its 'new' with the current setting before moving, or have sync_default() delete or refresh any pending task. The task also runs without the provisioning lock.
- Refuter: The sequence is reachable and nothing guards against it. The setting `focusmodenewcourses` has `set_updatedcallback('theme_dimensions_sync_focusmode_default')` (settings.php:419), and lib.php:359 passes the current setting value to `sync_default()`. Above the inline limit, `sync_default()` only queues the adhoc task and returns (focusmodefields.php:211-214). `checkbydefault` is not touched at that point, so the field still reads the old value. When the admin flips the setting back before cron, `sync_default(false)` reads `$old` from the field (still 0), sees `0 === (int) false` and returns at line 196 without touching the queued task. The task's `execute()` then calls `focusmodefields::set_default((bool) $data['new'])` straight from its stored custom data. It does not re-read the setting, and `set_default()` itself (line 271) does not either. The result is `checkbydefault=1` while the setting says off. The task also runs without the provisioning lock, as the finding says. Impact is narrow: existing courses keep their answer, because the old answer is materialised first. Only new-course form defaults and courses that are created without a row after that point read the wrong default. It also persists, because the next callback to the same value compares against the field and returns early. It clears only when the setting is toggled again. So it is a real race, but a low-impact one that needs a site above the inline limit and a quick toggle back before cron. I would rate it a risk, not a bug.
- Refuter's evidence: focusmodefields.php:195-199: `$old = $field->get_configdata_property('checkbydefault') ? 1 : 0; if ($old === (int) $new) { return; }`. materialise_focusmode_default.php: `focusmodefields::set_default((bool) $data['new']);` with no re-read of get_config('theme_dimensions','focusmodenewcourses'). Not checked: whether `queue_adhoc_task`'s dedupe with `$checkforexisting=true` could merge the tasks. It cannot help here, because the flip back never queues a task.

### 1.3 A refused lock drops the setting change silently
- File: `classes/local/focusmodefields.php:207` (batch b08), reported as **risk**
- Verdict: **confirmed**, severity after refutation: **risk**
- Evidence: $lock = self::get_lock(); if (!$lock) { return; }
- Suggestion: When another request holds the lock for 10 s, the admin's new default is saved in config but never reaches the field's checkbydefault, and nothing retries it. Queue the adhoc task, or report through debugging(), when the lock is refused.
- Refuter: The finding stands, but narrowly. sync_default() (classes/local/focusmodefields.php:204-207) is the only caller path from the setting's updated callback (lib.php:351-362, shim at :359). On a refused lock it returns with no write, no debugging(), no task queued. The admin setting `focusmodenewcourses` is already saved by then, so the setting says one thing and the field's `checkbydefault` keeps the old value. Nothing retries it. materialise_focusmode_default is queued only from the over-limit branch (:210-215), which sits after the lock, and the adhoc task never calls sync_default. No cron or reconcile path re-reads the setting.

The lock is contended only by ensure_fields() (:151, a brief field creation) and by another sync_default() running inline over up to MATERIALISE_INLINE_LIMIT = 500 courses (:67). That inline pass does 500 data_controller::save() calls, each firing events, so it can plausibly pass the 10 s wait (:289). A double save, or two admins saving, can therefore hit it.

Three things limit the severity. The window is narrow. The state self-heals: re-saving the setting recomputes `$old` from the field (:198), so `$old !== $new` and it runs again. And no existing course's answer is ever wrong, because materialisation had not started; only the default for new courses is stale. The comment at :153 ("nothing to do here") is accurate only for ensure_fields. The sync_default branch at :205-207 has no comment and drops the change without telling the admin.

I could not check how the lock factory behaves in production (db or file lock), or whether 500 saves really exceed 10 s on a real site. I did not look for a test that pins this branch.
- Refuter's evidence: classes/local/focusmodefields.php:204-207: `$lock = self::get_lock(); if (!$lock) { return; }` with `get_lock()` at :289 `->get_lock('focusmodefields', 10)`. lib.php:358-361 passes the already-saved setting into sync_default(); the adhoc task at classes/task/materialise_focusmode_default.php:60-81 is queued only after the lock is held.
